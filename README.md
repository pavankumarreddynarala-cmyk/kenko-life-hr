# The Kenko Life — HR & Asset Portal

A Next.js 15 portal for governed employee master data, fixed assets, employee-to-employee transfer approvals, onboarding, QR identification, and append-only audit history. PostgreSQL/Supabase is the system of record; the application does not silently fall back to local storage.

## Local setup

1. Copy `.env.example` to `.env` and provide `DATABASE_URL`, `DIRECT_URL`, and a 32+ character `JWT_SECRET`.
2. Install and prepare the database:

   ```powershell
   npm install
   npm run prisma:generate
   npx prisma migrate deploy
   npm run prisma:seed
   ```

3. Run `npm run dev`. The site root (`/`) redirects to the management sign-in (`/login`); employees use `/employee/login` for email OTP access.

The development seed creates administrator, HR, and CFO accounts with password `KenkoDemo!2026`. Remove or rotate these accounts before deployment. `OTP_PROVIDER=development` accepts the server-side `DEV_OTP` only outside production.

### Test employee OTP locally

The employee portal always needs PostgreSQL, including development OTP mode, because OTP attempts, employee lookup, onboarding, transfers, and audit events are persisted. A missing or unreachable database is shown as an actionable popup on `/employee/login` rather than a Next.js runtime overlay.

1. Copy `.env.example` to `.env.local`.
2. Set working `DATABASE_URL`, `DIRECT_URL`, and `JWT_SECRET` values.
3. Keep `OTP_PROVIDER=development` and choose a six-digit `DEV_OTP`.
4. Run `npx prisma migrate deploy`, then `npm run dev`.
5. Open `/employee/login`, enter any email address, and enter the configured `DEV_OTP`.

`OTP_PROVIDER` defaults to `development` only in non-production environments. Production requires an explicitly configured Supabase or Twilio provider and never falls back to development OTP.

## Portals, roles and sessions

| URL | Who | Notes |
| --- | --- | --- |
| `/` | everyone | Redirects to `/login`. |
| `/login` | Admin, CEO, COO, HR, CFO | Management sign-in. A signed-in manager is sent on to `/dashboard`. |
| `/dashboard`, `/employees`, `/assets`, `/transfers`, `/masters`, `/imports`, `/audit` | management | Guarded server-side; an employee session is redirected to the Employee Portal. |
| `/employee/login` | employees | Email OTP sign-in and first-time onboarding. |
| `/employee`, `/employee/employment`, `/employee/bank`, `/employee/assets`, `/employee/requests` | employees | One consolidated profile: personal details, HR-managed master data, bank/statutory, assets and requests. |

The two portals share no navigation links. Every page shows the signed-in person's name and login type in the left sidebar, with **Logout** directly beneath (and **Change password** for management accounts).

**Permissions.** Every management role can create, edit, transfer, import and export. Editing an **Employee Code**, **deleting/restoring assets** and **deleting master data** are limited to **Admin, CEO and COO** (`src/lib/permissions.ts` — one place to change this). The API enforces it; the UI only hides/disables the buttons.

**Inactivity timeout.** After 5 minutes without activity the browser shows a warning during the last minute and then signs the user out. The server enforces the same limit independently: the session cookie lives 6 minutes and is only renewed by `POST /api/auth/session`, which the browser calls while the user is active — background polling cannot keep an unattended session alive.

**Errors.** API failures return `{ error, code, fields[] }` with a plain-language message that names the field and says what to do; the UI shows them as popups and highlights the fields. Mandatory fields carry a red `*` and forms refuse to submit until they are filled in.

## Deletion history

Employees and assets are never hard-deleted. Deleting one requires a reason and keeps who deleted it, when and why (on the row and in the audit log); it disappears from the registers and reports but stays under **Show deleted employees / assets**, which offers *Details* (original record plus its full audit trail) and *Restore*. An asset that is currently assigned, or has a pending transfer, cannot be deleted. A deleted record keeps its unique values (Asset ID, mobile, PAN …) reserved, so restoring never collides with a newer record.

Master-data entries can be edited by any management role and deleted by Admin/CEO/COO. Entries used by employees or assets cannot be deleted (foreign keys are `ON DELETE SET NULL`, so this is checked in code); the message says how many records use it.

## Upgrading an existing database

Deploy the new migration before (or with) the new code: `npx prisma migrate deploy` applies `20260921000000_portal_overhaul_deletion_history` (adds `User.name`, deletion-history columns on `Employee`, and soft-delete columns on `FixedAsset`).

## Employee Code, Team Office Code and Organisation Code

Employee Code is generated by PostgreSQL (`EMP0001`, `EMP0002`, …) and can be overwritten by an Admin/CEO/COO (unique, 2–20 characters of capitals, digits and hyphens). **Team Office Code** is the separate punching-system code. The **Organisation Code** (formerly "CODE") is derived from master data and follows any change to the Employee Code or to a master's code. It is recalculated from controlled master data in this exact order:

`CITY-OUTLET_MODEL-SPECIAL_OR_AREA-NO_OF_OUTLETS-DEPARTMENT-EMPLOYEE_ROLE-EMPLOYEE_NUMBER`

For example, Employee Code `EMP0001` with the corresponding configured codes becomes `BLR-COR-IDN-1-TCWG-CEO-0001`. The Organisation Code remains empty until every dependent field is configured. CTC fields are intentionally not part of this portal.

## OTP provider setup

Set exactly one `OTP_PROVIDER`:

| Provider | Required variables | Setup |
| --- | --- | --- |
| `supabase` | `SUPABASE_URL`, `SUPABASE_ANON_KEY` | Uses Supabase Auth's email OTP (`/auth/v1/otp` with `email`, `type: "email"`). No extra Supabase Auth feature needs enabling. |
| `twilio` | `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_VERIFY_SERVICE_SID` | Create a Twilio Verify service with an email channel configured (Twilio Verify + SendGrid integration). |
| `development` | `DEV_OTP` | Local/private development only; the server rejects this provider in production. |

No provider error falls back to another provider. Secrets belong in the deployment secret store and local `.env`, never in source control.

## Supabase deployment

1. Create a Supabase project and copy its pooled connection string to `DATABASE_URL` and direct connection string to `DIRECT_URL`.
2. Run `npx prisma migrate deploy`. The baseline migration creates relational foreign keys, unique and partial indexes, domain checks, generated timestamps, the Employee Code sequence/CODE trigger, and RLS.
3. Run `npm run prisma:seed` only for a private demo. Do not seed production.
4. Configure the selected OTP provider and deploy the Next.js server with the same environment variables.

The server uses Prisma through the database owner/service connection. RLS denies direct PostgREST access by default and exposes read-only policies for authenticated Supabase users on non-sensitive master/asset tables. Employee portal authorization is enforced again in server routes using httpOnly signed sessions and ownership checks.

## Main workflows

- **Dashboard:** every figure, alert and recent-activity line is computed from the database and the audit log.
- **Employee Master:** governed master dropdowns, Team Office Code and dynamic Organisation Code, add/edit, delete with deletion history, full per-column filters, masked exports.
- **Asset Register:** grouped columns matching the add form, add/edit/delete, ITC amount only when ITC Eligible = Yes, deletion history, full per-column filters, stable QR detail links, labelled SVG downloads.
- **Transfers:** management transfers with effective/registered dates and editable history; employee outgoing/incoming requests with recipient approval or decline. Assignment, status, event, and audit writes share a transaction.
- **Employee Portal:** email OTP, existing-employee detection, validated Indian onboarding, a consolidated profile, My Assets, and Requests.
- **Audit:** actor, role, action, entity, timestamp, and before/after/details for portal mutations.
